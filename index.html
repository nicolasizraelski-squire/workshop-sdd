The Concept

What is Spec-Driven Development?

A workflow where you invest in detailed specifications before any code is written. The AI implements from the spec, not from vague prompts.

“Specifications are durable; prompts are ephemeral. Think thoroughly first, build confidently after.”

The Concept

What goes into a spec?

A spec is not a prompt. It's a structured document that captures decisions.

Always include
  • 📌 User flows — step by step, screen by screen
  • 📌 Acceptance criteria — what "done" looks like
  • 📌 Edge cases — errors, empty states, permissions
  • 📌 API contracts — endpoints, payloads, responses
  • 📌 Design references — Figma links, exact copy
When applicable
  • 📍 Role-based permissions matrix
  • 📍 State diagrams — what triggers what
  • 📍 Data model changes
  • 📍 Migration / backward-compatibility notes
  • 📍 Known gotchas from existing codebase

The spec is written in Markdown. It lives in version control. Anyone can read it.

The Concept

From spec to plan

A spec defines what to build. A plan defines how and in what order.

Spec
→
Plan
→
Implement
The spec answers
  • 📝 What are we building?
  • 📝 What should it do? (acceptance criteria)
  • 📝 What can go wrong? (edge cases)
  • 📝 What does it look like? (Figma)
The plan answers
  • ⚡ What do we build first? (dependencies)
  • ⚡ What already exists? (reuse opportunities)
  • ⚡ What's shared across tickets? (infra)
  • ⚡ How do we break it into phases?

Without a plan, even a great spec leads to disorganized implementation. The plan turns the spec into actionable, ordered work.

The Concept

Key principles

Rules that make SDD work in practice — for any team, any codebase.

📑 1 ticket = 1 spec
Each independently demo-able flow gets one specification and one ticket. No ambiguity about scope.
🔍 Reuse first
Always search the existing codebase before creating new components. AI tends to create new things by default — tell it to look first.
🎨 Respect design
Designs are not suggestions. Exact copy, spacing, colors, interactions — the spec references Figma frames directly.
📝 Document gotchas
Record discoveries after every phase. Prevent the next person from re-discovering known issues.

When applied correctly, the spec is a reflection of the code — written in Markdown.

The Concept

Who benefits from SDD?

SDD is not just an engineering practice. It improves alignment across the entire team.

💻 Engineers
Implement from clear requirements instead of guessing. Less rework, more confidence.
📋 Product
Get real documentation in Jira — acceptance criteria, flows, edge cases — not just ticket titles.
🔎 QA
Know exactly what to test. Acceptance criteria are defined before implementation starts.
🎨 Design
Fidelity is enforced. The spec references Figma directly — no "close enough".

SDD creates a shared source of truth that everyone can reference — before, during, and after implementation.

The Concept

When should you use SDD?

Use SDD
  • ✅ Feature touches 3+ screens
  • ✅ Multiple user roles or permissions
  • ✅ Cross-team handoffs (eng → QA → product)
  • ✅ Architecture decisions that affect future work
  • ✅ Would take more than a day to implement
Skip SDD
  • → Isolated bug fixes
  • → Styling tweaks
  • → Single-file refactors
  • → Quick prototypes / spikes

Rule of thumb: If you'd spend more than a day implementing it, spend a few hours speccing it first.
