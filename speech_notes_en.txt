SLIDE 2 — Title: "Stop prompting. Start specifying."
------------------------------------------------------
[Opening slide — let it sit for a few seconds before speaking.]

"Alright, welcome to session 4. Today we are going to talk about something I think it will really change the way we work with AI on our day to day. So as it says right there, stop prompting and start specifying. Today I want to start with a quick story, because just so you know, this session may sound very technical and it's especially useful for engineers, everyone in the team can find it valuable."

[~30 seconds]


SLIDE 3 — "My mom asked me: I still don't understand what you do at work"
---------------------------------------------------------------------------
"Just a quick story. The other day I was talking with my mom, and she asked me the typical question: I don't understand what you do at work? So I explained, I work with code, I use AI, I build a software product, etcetera. But she was like, Nah I still don't understand! So all of a sudden I found myself explaining spec driven development to her. She owns a notions store, they sell sewing supplies, clothing materials, and they do clothing repairs. So I told her, imagine you could outsource the repairs to someone who is faster, more precise, and can handle much more volume than you. Sounds great right? The catch is that they don't know your customers, their preferences, or your business. They execute perfectly. But they don't know what to execute."

[~2 minutes]


SLIDE 4 — "Two questions"
---------------------------
"So you have two options: 1. You can review every stitch they make, sit next to them and correct every detail. Knowing that their execution will be almost always better than yours. 2. Or you can spend that time in writing a clear specification of what you need. Tell them 'these pants needs this type of stitch' or 'the length has to be exactly this one' or 'if the fabric is damaged, ask me before doing anything'. In other words, expected results, edge cases, acceptance criteria. That is Spec driven development, instead of asking the AI to do something and spend time reviewing and fixing line by line, we spend that time thinking through the problem before a single line of code gets written."

[~2 minutes]


SLIDE 5 — "Models are great at generating code..."
----------------------------------------------------
"Because this is a reality, models are really good at generating code. They write code that compiles, that has a lot of tests, but that is not the same as building a good software product.

Models have a limited context window, they don't know your whole architecture. They generate correct code, but they don't know the business rules and constraints of the real product. So going back to the analogy, they execute perfectly, but they don't know what to execute. The question is how do we close that gap?"

[~1.5 minutes]


SLIDE 6 — "What is Spec-Driven Development?"
----------------------------------------------
"Specification driven development is a workflow where we invest most of our time in writing detailed specifications before any code gets written. Think about how most devs work with AI today. They open Cursor, or Claude, type build me a login page, and the AI starts generating code right away. Sometimes it works, most of the time it doesn't. And when it doesn't they start iterating 'No, add this' 'Oh I forgot about this case' 'Change this'. SDD proposes something different. The core idea is that specifications are durable, they stick around, they get versioned and shared. Prompts are ephemeral and get lost between sessions. The idea is to think well first, and build confidently after."

[~2 minutes]


SLIDE 7 — "The SDD mindset shift"
-----------------------------------
"Here we can see the evolution of how we work with AI.

On the far left, we have 'reviewing every line'. It's like reviewing every stitch your tailor makes. It doesn't scale.

Then comes iteration mode: you prompt, see the output, adjust, re-prompt. You get closer, but you've burned four or five rounds just to get to something acceptable.

Then there are better prompts. You write more detailed prompts, with more context. I mean, it helps a lot and your prompt starts looking like the kind of spec we're going to build later. But the problem is that prompts are ephemeral. If tomorrow you open a new session, that prompt is gone. And on the far right is SDD. You write specs that persist, that can be versioned in Git, that can be shared with your entire team. This way, the AI's job becomes obvious and it doesn't have to guess anything. What I want you to see here is that this is not about writing better prompts. It's about changing where you are investing your time. The input determines the output, so don't be afraid to spend days without writing a single line of code, if you are writing the right specs."

[~2.5 minutes]


SLIDE 8 — "What goes into a spec?"
-------------------------------------
"But what does a spec actually contain? A spec is not a long prompt. It's a structured document that captures decisions. Here I have to make a clarification: There is no single type of spec, that will depend a lot on what you are building. So don't be afraid to tell the model what you want to build, and then, lean on it to help you put the spec together.

However there are some things that are almost always going to be included, for example. 1. User flows, screen by screen. 2. Acceptance criteria, what does Done mean in this feature. 3. All the edge cases. 4. API contracts, the payloads, the responses. 5. If you are building front end, the design references, the link to the Figma designs in our case. In addition you can sometimes add permissions matrix, state diagrams, known gotchas from previous phases.

Over time you will figure out what's useful to include for your use cases. And who knows, you can create a skill that asks you those things and creates the spec for you."

[~2.5 minutes]


SLIDE 9 — "From spec to plan"
-------------------------------
"Ok, we are done with the spec, but the spec alone is not enough. We need a plan. The spec answers WHAT we are building, what should it do, what can go wrong, etcetera. The plan answers HOW we are going to build it, in what order. Which things are already created, how are we going to break the feature into phases.

Something really valuable happens at this stage. When the model analyzes the spec to generate the plan, it catches gaps. It can catch things that were left ambiguous, edge cases that weren't covered. So it asks you: 'What should we do in this situation' 'The endpoint response includes pagination, what should we do here'. It's like a second pair of eyes reviewing each spec before a single line of code is written.

With no plan, even an excellent spec leads to a messy implementation. The plan turns the spec into actionable ordered work, and along the way it closes the gaps that were left behind."

[~2.5 minutes]


SLIDE 10 — "Key principles"
-----------------------------
"There are three principles that will help you implement SDD in almost any team and any codebase.

1. One ticket means one spec: Each demonstrable flow gets one of each, and this way we eliminate scope ambiguity.
2. Reuse first. Always search the codebase for existing components. We know AI tends to create new things by default. If you don't explicitly tell it 'check if this already exists first,' it'll invent a new component every time.
3. And third, document gotchas, record what you discovered so the next person who touches the feature doesn't rediscover the same problems.

So when you do this well, the spec will mirror the code."

[~2.5 minutes]


SLIDE 11 — "Who benefits from SDD?"
--------------------------------------
"SDD is not just for engineers. It benefits the entire team. Engineers benefits are clear, we can implement from clear requirements, less rework and more confidence. Product gets real documentation, acceptance criteria, edge cases. Not just a ticket title. Product still makes the business decisions, but now those decisions are documented. QA knows exactly what to test and how of every feature.

And design gets the peace of mind that fidelity is enforced."

[~2 minutes]


SLIDE 12 — "When should you use SDD?"
--------------------------------------
"So SDD is not for everything, we don't want to add unnecessary bureaucracy when is not needed. Use it when you are implementing a feature that touches multiple screens, when there are handoffs between teams, or when there are architectural decisions. Don't use it for isolated bug fixes, styling tweaks, or single file refactors. Use the rule of thumb: if you are going to spend more than a day implementing it, spend a few hours creating the spec first."

[~1.5 minutes]


SLIDE 13 — "This is a movement, not just our idea"
---------------------------------------------------
"This is a whole movement, it's being adopted across the industry. GitHub launched Spec Kit, I've heard that for some use cases it adds more bureaucracy than needed, but you know, it's out there. We also have GSD that I remember Arthur also referenced it on previous sessions. It's the most popular SDD framework for Claude Code so far. And Superpowers is a Claude plugin that enforces planning, TDD, and code review. It's more opinionated, but for teams that want rigid structure it works well. The links are right there if you want to explore them. The idea is that each team can adapt the tools to best match their workflow."

SLIDE 15 — "The starting point" (Case Study)
----------------------------------------------
"So, now I want to tell you about how we applied SDD on the Commander rewrite, so you also walk away with a real example. The context is that we are rebuilding Commander and we had to gather information from two different legacy codebases. That means years and years of features stacked one on top of the other.

Zero documentation and all the flows, business rules, edge cases were all buried in the code. There was no single place to look up what we needed. Engineers knew the code, product knew the business but it was really hard to put the full picture together.

Early on, we tried prompting Cursor, and then Claude to rebuild features, but without documentation it hallucinated business rules and missed edge cases constantly, which made us iterate a lot."

[~2.5 minutes]


SLIDE 16 — "How we applied SDD" (Case Study)
----------------------------------------------
"So we changed our approach. First we used Claude as an archaeology tool. We pointed it at the existing codebases and asked it to document what it found (flows, business rules, edge cases, etc). We didn't ask it to build anything, just read and document.

Second, we took those extracted specs and refined them with our new requirements. We kept the business rules, the endpoints, the API contracts and everything else, but just using our new requirements, design and flows. After that, each spec became the single source of truth for the feature.

And third, we generated the implementation plan that broke each feature into small and testable phases. We'd implement one phase at a time, verify it worked, and then move on to the next one.

Basically, we went from spending a lot of time iterating and going back over the same ground, to spending that time thinking through the specs and working through the questions as they came up. That's what allowed us to drastically reduce the time per feature.

And I want to be clear: this workflow applies to any team building features with AI. Maybe in your case step one doesn't exist. You may not have legacy code to extract specs from. Maybe your starting point is a PRD or a Jira ticket. That's great too. You can take it, refine it, fill in what's missing, and run it through the same flow: spec, plan, implement in phases. What changes is the starting point, not the process.

Once you are implementing, the cycle is: you implement a phase, validate what it did, and if something is off, you fix the spec and then the code. The spec should always be updated."

[~3.5 minutes]


SLIDE 17 — "The results" (Case Study)
---------------------------------------
"Here you have some of the results. We are cutting the PR cycle by four times. PRs are merging faster because the scope is clear from the start, and everything has been tested and considered upfront. Edge cases, user permissions, etc. And to put it in a concrete example, before SDD, shipping the complete client membership flow took us 42 days. After SDD, we shipped Product support in checkout, a feature with more lines of code, in just 10 days. Obviously, the features are different and not directly comparable, but we saw a clear tendency toward reducing the delivery times.

We shipped roughly twice as many features in the 8 weeks after SDD compared to the 8 weeks before. The team also grew in this period, but having a detailed framework also help the new ones to step into the cycle with no problem at all. And last but not least, we went from zero specs in the repo to 49 in version control, and then this lead to Jira tickets fully completed. And for anyone who wants to know more about the framework we are using, you will find the step-by-step guide with the skills, the templates, and the whole workflow we are using across the team in this link."

[IF THEY ASK: The per-developer rate also went up about 24%, so it's not just headcount. The key is that new hires shipped fast because they had specs to work from. Without SDD, onboarding four people in two months usually slows you down.]

[~3 minutes]


SLIDE 18 — "Meet /build-spec"
-------------------------------
"Now, for this session I wanted you to walk away with something you can actually use today. So I built build-spec, a skill that is already up on our marketplace, you can start using it right away.

The skill has three phases. First discover. It reads your codebase, understands the structure, the patterns and the components that already exist. Second, it asks you questions adapted to the domain, so if it is backend it asks about endpoints and permissions, and if it is front end it will ask you about Figma and UI states. And third, it generates the spec and the implementation plan. Without the spec Claude would start coding right away, no question asked. The rework will be inevitable. With the skill, you will have to answer a battery of questions before a single line of code gets written."

[~2 minutes]


SLIDE 19 — "/build-spec in action"
------------------------------------
"Here you can see the skill in action in the terminal. First it scans the project, detects the stack, understands how the code is structured and finds existing components. Then it starts asking you meaningful questions — not generic ones, but concrete things about what you want to build, how you want to build it, what permissions apply, how it should behave in different scenarios, etc. They're questions that make sense because it has already read your codebase. After that you can see that it will build the Spec and plan.

Once you are happy with that, you can start with the implementation phase by phase. Here it is when everything we saw in previous sessions comes in. You can use agent teams, sub agents, skills and everything. The spec will be the input, and all these tools are going to be the engine for this implementation.

So the skill is already available through the skills marketplace. So you can test it and feel free to propose any improvement you find. I want to add a disclaimer that this skill is a solid starting point, but maybe the best approach is to fork it and build one that fits your team's workflow."
